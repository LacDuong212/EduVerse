## Bugs Found

### EDV-268 — [Medium] Notification: markAsRead controller uses document as count — response message corrupted and full doc leaked in result

**File**: `src/modules/notification/notification.controller.js` → `markAsRead`  
**Root cause**: `notifService.markOneAsRead()` returns the updated Mongoose document (via `findOneAndUpdate({ new: true })`). The controller names the return value `markedCount` and uses it as a number. Because `document === 1` is always `false`, the plural suffix `"s"` is always appended, corrupting the message to `"Marked [object Object] notifications as read!"`. The full document (including `_id`, `__v`, `user`, `createdAt`, `updatedAt`) is also forwarded as `res.body.result`, leaking internal fields.  
**Expected**: `result` = `1` (number), `message` = `"Marked 1 notification as read!"`  
**Actual**: `result` = raw Mongoose document, `message` = `"Marked [object Object] notifications as read!"`  
**Status**: Jira EDV-268 filed — intentional-fail test in place

---

### EDV-269 — [Low] Notification: GET /notifications ignores ?limit query param — validated value never passed to service

**File**: `src/modules/notification/notification.controller.js` → `getMyNotifications`  
**Root cause**: The route registers `validate(notifSchema.limitQuery)` which parses and coerces the `?limit` query param, storing it in `req.validated.query.limit`. However, the controller calls `notifService.getUserNotifications(userId)` without forwarding the validated limit. The service always defaults to `50`.  
**Expected**: `GET /api/notifications?limit=2` returns at most 2 items  
**Actual**: All notifications returned (up to 50), limit silently ignored  
**Status**: Jira EDV-269 filed — intentional-fail test in place
