## 6. Bugs Discovered in Production Code

### EDV-266 [High] — Coupon: usersUsed.includes(userId) always false due to ObjectId vs string mismatch

**File:** `src/modules/coupon/coupon.service.js` → `applyCoupon`

**Root cause:** `Coupon.findOne({ ... }).lean()` returns `usersUsed` as an array of `mongoose.Types.ObjectId` objects. The guard `coupon.usersUsed.includes(userId)` compares these ObjectId objects with `userId` (a plain string from `req.user.userId`). `Array.prototype.includes` uses strict equality (`===`) — ObjectId objects never equal strings. The check always returns `false`, so a student who has already used a coupon can apply it again via `POST /api/coupons/apply`.

**Note:** This does NOT affect `validateCoupon` (used in order checkout) — that function uses a MongoDB query filter `usersUsed: { $ne: userId }` which correctly compares at the DB level.

**Status:** Documented. No runnable intentional-fail test (no DB fixture with student in `usersUsed`, and since the bug prevents that from being meaningful). Jira: EDV-266.

---

### EDV-267 [Medium] — Coupon: validateCoupon skips startDate check — coupon usable before activation via order flow

**File:** `src/modules/coupon/coupon.service.js` → `validateCoupon`

**Root cause:** `validateCoupon` (called by `placeOrder` during checkout) only verifies `coupon.expiryDate < new Date()`. It does NOT check whether `now < coupon.startDate`. By contrast, `applyCoupon` correctly rejects with 400 'This coupon is not active yet'. This inconsistency means a coupon with a future `startDate` can be applied when placing an order, bypassing the intended activation schedule.

**Status:** Documented. No runnable intentional-fail (no coupon with future `startDate` in DB). Jira: EDV-267.
